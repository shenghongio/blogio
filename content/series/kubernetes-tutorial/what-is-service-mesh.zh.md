> 服务网格把服务间通信从「基础设施的副产物」变成「可被策略管理的显式对象」。

在 Kubernetes 里，服务间通信默认由 kube-proxy 与 CNI 插件完成。这套机制解决了「能通」的问题，但没有解决「如何可控地通」的问题：流量路径不可观测，加密需要应用自己实现，重试、熔断、超时策略分散在每一份业务代码中。服务网格的出现，正是为了把这些横切关注点从应用中剥离出来，下沉到基础设施层统一治理。

## 核心机制

服务网格的实现方式各不相同，但都要解决同一个结构性问题：如何在不侵入业务代码的前提下，对每一次服务调用施加统一的策略。

### 边车代理与流量拦截

主流实现采用边车（sidecar）模式：为每个 Pod 注入一个代理容器，通过 iptables 或 eBPF 规则把进出流量重定向到代理。应用对此无感知，仍然使用普通 HTTP/gRPC 调用，而加密、重试、遥测全部由代理完成。

这种方式的好处是语言无关——无论是 Java、Go 还是 Python 服务，治理能力都一致。代价是额外的资源开销与调用链路中的一跳延迟。

### 服务身份与双向 TLS

传统 TLS 依赖证书与域名，而服务网格引入「服务身份」这一抽象：每个工作负载获得一份由网格签发的证书，证书中编码其服务账号。mTLS 握手时双方互相验证身份，而非仅仅验证加密。

这让「只允许 A 服务访问 B 服务」这类策略有了密码学基础，而不是依赖 IP 白名单这种易于伪造的手段。

### 流量策略作为声明式对象

熔断、超时、重试、限流这些策略在服务网格中变成了声明式的 CRD。运维人员以 YAML 描述期望行为，由网格的控制器将其翻译为代理配置并下发。策略与应用生命周期解耦，变更无需重新构建镜像。

## 与相关概念的边界

容易混淆的是服务网格与 API 网关、CNI 插件的职责划分。

### 与 API 网关的区别

API 网关面向集群边界，处理南北向流量：外部客户端如何进入集群、如何认证、如何限流。服务网格面向集群内部，处理东西向流量：服务之间如何通信。两者经常配合使用，但治理对象完全不同。

### 与 CNI 插件的区别

CNI 负责三层/四层连通性与网络策略，管的是「数据包能否到达」。服务网格工作在七层，管的是「请求如何被处理」——路由、重试、加密。二者互补，eBPF 类 CNI 甚至能替代部分边车职能，但七层语义治理仍在网格层完成。

## 何时值得引入

服务网格不是默认必需品。它的价值随服务数量与团队规模增长而显现。

值得引入的典型信号包括：服务数量超过数十个、多语言技术栈导致治理逻辑难以统一、合规要求服务间通信必须加密、需要精细化的调用链追踪。反之，若系统只有少数几个服务、团队单一，引入网格带来的运维复杂度往往超过收益。

选型时的关键考量不在于功能清单的长度，而在于：控制面是否足够轻量、数据面开销能否接受、与现有可观测体系能否打通、以及故障时的降级路径是否清晰。服务网格本身就是一个关键的调用链路节点，它的可靠性必须高于它所承载的业务。
