> 安全不是某个组件的附加能力，而是贯穿集群全生命周期的设计前提。

Kubernetes 的安全体系建立在一个核心假设之上：集群内部并非可信区域。默认配置下，Pod 之间可以自由通信，容器以较高权限运行，API Server 也可能暴露在不受控的网络中。生产环境的安全工作，本质上是在这个默认不安全的基线之上，逐层收紧暴露面与权限边界。

## 安全的分层视角

理解 Kubernetes 安全，最有效的方式是按层次拆解。每一层都有独立的威胁模型与防护手段，任何一层失守都可能导致整体防线瓦解。

### 集群基础设施层

这一层关注控制平面与节点的可信性。包括 API Server 的访问控制、etcd 的静态加密、kubelet 的认证配置，以及节点操作系统的补丁基线。控制平面一旦被攻破，整个集群即视为完全失陷，因此这一层往往是攻击者的首选目标。

### 工作负载层

这一层关注 Pod 与容器自身的运行约束。关键问题包括：容器是否以 root 运行、是否具备提权能力、能否访问宿主机资源、镜像是否来自可信来源且无已知漏洞。Pod Security Standards 与 RuntimeClass 是这一层的主要抓手。

### 网络层

这一层关注流量的可见性与可达性。默认的扁平网络模型意味着任何 Pod 都能与任何 Pod 通信，这在多租户场景下是不可接受的。NetworkPolicy 提供服务间的访问控制，而服务网格则进一步提供服务身份与双向 TLS。

### 身份与权限层

这一层关注「谁能做什么」。RBAC 负责 API 层面的授权，ServiceAccount 为工作负载提供身份，而外部身份系统则需要通过 OIDC 或 Webhook 与集群对接。最小权限原则是这一层所有配置的共同基准。

## 从策略到实践

分层模型解决的是「在哪里设防」，真正落地还需要回答「如何持续验证」。静态配置只能证明某一时刻的状态，而威胁是持续演进的。

### 准入控制作为闸门

Validating Admission Policy 与 OPA Gatekeeper 能在资源创建与更新时执行策略检查，把安全约束前移到部署阶段。相比事后审计，准入控制能在不合规配置进入集群之前就直接拒绝。

### 运行时检测作为补充

Falco 等运行时安全工具通过系统调用行为建模，识别异常进程执行、敏感文件访问与异常网络连接。准入控制管的是「允许什么进来」，运行时检测管的是「进来之后做了什么」。

### 供应链完整性

镜像签名、SBOM 生成与来源验证构成了供应链安全的三个支柱。Sigstore 与 Cosign 提供了无需集中式信任锚的签名方案，使得从构建到部署的每一环都可被追溯与验证。

## 常见认知误区

+ 认为启用 RBAC 就等于解决了权限问题：RBAC 只约束 API 访问，不约束容器运行时能力
+ 认为 NetworkPolicy 能覆盖所有流量：它依赖 CNI 实现支持，且不处理宿主机网络与外部流量
+ 认为镜像扫描通过即代表安全：扫描只反映已知漏洞，无法覆盖零日与配置错误
+ 认为单集群隔离足够：多集群共享身份体系时，横向移动风险仍然存在

安全建设的价值不在于堆叠工具，而在于让每一层的假设都显式可见、可验证、可审计。
