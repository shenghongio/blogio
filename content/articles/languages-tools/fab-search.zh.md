## 起点：搜索不该有两个入口

浮窗导航最初的做法是：右上角单独挂一个搜索按钮，点开弹出一个独立的搜索浮层。问题不在于"能不能用"，而在于**它分裂了导航的心智模型**——用户点「首页」是展开浮窗，点搜索却是弹出另一个东西，两个交互看起来相似，行为却完全不同。

更麻烦的是视觉层级。弹出浮层时底下的分类区还在，中间隔着一层磨砂。用户的注意力被迫在两块内容之间来回切换：我是在看分类，还是在看候选？

所以这次的做法是把搜索**收进浮窗本体**：不弹层，直接就地替换。

## 双 pane：同一块区域，两种内容

浮窗的内容区被划成两块 pane，同一时刻只显示一块：

```
┌─────────────────────────────────────┐
│  ⌂ 首页  │  ⌕ 搜索文章…              │  ← 顶栏常驻
├─────────────────────────────────────┤
│  导航 pane      （分类网格）          │  ← 无输入时显示
│  搜索 pane      （候选列表）          │  ← 有输入时显示
└─────────────────────────────────────┘
```

顶栏始终包含搜索输入框，内容区按输入状态切换。没有浮层、没有遮罩、没有磨砂，就是简单的显示/隐藏。

```go
if (query) {
    navPane.hidden = true;
    searchPane.hidden = false;
} else {
    navPane.hidden = false;
    searchPane.hidden = true;
}
```

## 关键问题：高度为什么会跳

这是整个改造里最难缠的部分。最初候选 pane 是自然高度，内容多就撑高、内容少就收缩。结果输入第一个字母时，面板**瞬间从分类区高度跳到候选区高度**，几乎撑满半个视口。

原因很直白：候选列表天生比分类区高。这不是计算错误，是布局本身就在"长得不一样"。所以无论怎么调 JS 都治不了。

中间试过用 JS 读取导航区的 `scrollHeight`，在切换前把容器高度写死。但打开瞬间布局还没稳定，读到的数值偏差极大，反而把面板设到了接近视口上限的值，跳得更厉害。

最终的做法是**只锁一次，锁真实的渲染高度**：

```go
var lockHeight = function(){
    if (!navBody) return;
    var h = navPane.getBoundingClientRect().height;
    if (h > 0) navBody.style.height = h + 'px';
};
```

在切换到候选区**之前**读取导航区的真实高度，写进容器。此后无论候选多少，容器高度恒等于分类区高度。

## 让候选在框内滚动，而不是撑大容器

锁定容器高度还不够，还得阻止 pane 自己撑大它。两块 pane 都改成撑满容器、各自滚动：

```css
.gs-stack-modal-body {
    max-height: calc(100vh - 200px);
    overflow: hidden;
    display: flex;
    flex-direction: column;
}

.gs-stack-nav-pane,
.gs-stack-search-pane {
    flex: 1 1 auto;
    min-height: 0;
    overflow-y: auto;
    scrollbar-gutter: stable;
}
```

`min-height: 0` 是 flex 布局里必须加的一条：flex 项默认 `min-height: auto`，会拒绝收缩到内容以下，导致容器被顶开。`scrollbar-gutter: stable` 则是另一个细节——滚动条出现时会占掉宽度，没有这条，列表一长就会产生横向抖动。

## 键盘与鼠标的高亮之争

候选支持 ↑ ↓ 选择、Enter 跳转、Esc 收起。这里踩了一个隐蔽的坑：按下 ↓ 后 `scrollIntoView` 会让列表滚动，滚动又会持续触发 `mousemove`，而原来的监听无条件把高亮塞回鼠标所在行。

结果就是键盘往下走，中间某条却顽固地留着灰底——两个高亮源在打架。

解法是给鼠标加一个"接管状态"：

```go
searchResults.addEventListener('mouseenter', function(e){
    if (e.target.closest('.gs-search-result')) mouseMode = true;
}, true);

searchResults.addEventListener('mousemove', function(e){
    if (!mouseMode) return;
    ...
});
```

只有鼠标真正进入候选区才置为 `true`；按 ↑ ↓ 立即置为 `false`，此后滚动产生的事件一律忽略，直到鼠标重新移入。每次重新渲染结果也重置，避免新列表在光标下方被误选。

## 候选行里该显示什么

最后的改进是候选条目的信息密度。原来的候选只有标题和归属徽章，用户知道"这条匹配了"，却不知道"匹配在哪"。

现在每个字段单独检查命中，并在右侧给出上下文摘录：

```
安全概述  (Kubernetes 教程)      [正文]  …默认配置下，Pod 之间可以自由通信…
```

摘录以关键词为中心向两侧扩 34 个字符，截断处加 `…`；整行强制单行省略，条目不换行、高度固定，滚动列表不会抖。命中字段用蓝色药丸标明，与橙色的 `tcf`、青色的 `section` 归属徽章明确区分——前者说"为什么被搜到"，后者说"它属于谁"。

## 小结

这次改造没有引入任何新组件，只是把搜索从"另一个浮层"变成"同一面板的另一种状态"。真正花时间的地方不在功能，而在**布局的稳定性**：高度锁一次、pane 允许收缩、滚动槽位预留、高亮源收敛。

界面上的"不跳"，背后是这四条约束同时成立。
