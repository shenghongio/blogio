## 现象：样式像完全没被加载

文章列表页刚写完，打开预览却看到完全错误的样子：布局没有分栏，所有元素从上到下单列堆叠，左侧分类名变成了普通列表项，缩略图撑成了大图。

第一反应是"CSS 没加载"，但页面明显套用了其他样式——字体、间距、面包屑都对，只是**新写的那部分完全不见了**。

这就排除了加载失败的可能：如果整个文件没加载，所有样式都该丢失，而不是精确地只丢后半段。

## 第一层排查：样式写进去了吗

先确认样式确实在文件里、也确实被引用：

```bash
grep -n "article-index" assets/css/custom.css
```

结果是存在的，在文件第 6586 行附近。再确认模板引用无误：

```go
{{ $customCSS := resources.Get "css/custom.css" }}
{{ $customCSS = $customCSS | minify | fingerprint }}
```

这部分一直是好的。既然源文件里有、也被正确引入，那问题就在**CSS 解析阶段**。

## 第二层排查：大括号配平

CSS 解析失败最常见的原因是括号不匹配。统计一下：

```bash
python3 -c "
s = open('assets/css/custom.css').read()
print(s.count('{'), s.count('}'))
"
```

输出是 `1137 1138`——**少了一个左括号，多了一个右括号**。也就是说，文件里存在一个未闭合的规则块。

缺口在文件很靠前的位置并不致命，CSS 会继续往后解析；但如果缺口没闭合，后续内容就会被当作这个规则块的**内部声明**。而普通规则块内部只能放 `property: value`，遇到 `.article-index {` 这样的新选择器时，整段都会被丢弃。

这正好解释了观察到的现象：前半段正常，从缺口的规则块之后全部失效。

## 定位：缺口在哪儿

`{` 少了但 `}` 多了，说明有一条规则的右括号被"挪用"了——它实际闭合的是上一条规则。

往前翻查，问题出在样式文件的末尾附近：

```css
body:has(.gt-page--standalone) .gt-chapter:hover {
    border-left-color: #7c4dff;
    box-shadow: 0 6px 24px rgba(0, 0, 0, 0.5);
    /* ← 这里缺少一个 } */
```

这条 `.gt-chapter:hover` 规则写到这里就结束了，但右括号没写。而我在它后面追加新样式，新样式的第一个 `}` 就"顺手"闭合了这条旧规则。

于是 `.article-index` 到那一整段，全部变成 `.gt-chapter:hover` 的内部声明，被解析器丢弃。

## 修复

补上缺失的 `}`：

```css
body:has(.gt-page--standalone) .gt-chapter:hover {
    border-left-color: #7c4dff;
    box-shadow: 0 6px 24px rgba(0, 0, 0, 0.5);
}
```

再验证配平：

```bash
open  : 1138
close : 1138
diff  : 0
```

重新构建后，新规则出现在产物的 CSS 里：

```bash
grep -c "article-index" public/css/custom.min.*.css
```

## 为什么这个错误能潜伏这么久

值得注意的是，这个缺口不是这次新加的，而是**历史遗留**。它在 `.gt-chapter:hover` 之后就一直存在，只是后面没有写任何新样式——空白区域里没有 `{`，所以那个多出来的 `}` 也就没人"挪用"，文件看起来一切正常。

缺口的破坏性只在**追加内容时**才显现：新内容的第一段会被吞掉，把它当成旧规则的延续。也就是说，这类错误的表象总是"新样式不生效"，而不是"旧样式出问题"，很容易把排查方向引向刚写的代码。

## 教训

- 追加样式前先跑一次括号配平。一次 `count('{') - count('}')` 的成本，远低于从现象反推根因。
- "部分样式失效"几乎总是解析问题，而不是加载问题。加载失败是全丢，解析失败才会只丢一段。
- 报错位置通常不在真正的错误位置。解析器不会告诉你"这里少了个括号"，它只会在下一段被吞掉的地方表现异常。

工具不会替你在意配对，但这个数字会。
